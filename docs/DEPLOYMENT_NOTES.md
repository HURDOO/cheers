# 배포 연결 시 확인할 사항

현재 `공개` 동작의 범위는 로컬 콘텐츠 릴리스와 테스트 사이트 데이터 갱신까지다. 운영 이미지 게시, 원격 서버 배포와 도메인 공개는 아직 연결하지 않는다.

## 현재 경계

- 편집 정본: `content/editorial/`
- 불변 공개 이력: `content/releases/<release-id>.json`
- 빌드 입력: `src/data/generated/catalog.json`
- Admin의 `공개`·`재공개`·`공개 내리기`는 위 파일만 갱신한다.
- Vite 개발 서버는 생성 카탈로그 변경을 감지해 로컬 화면을 갱신한다.
- 정적 프로덕션 결과물은 새 카탈로그가 포함된 빌드를 다시 배포해야 바뀐다.

## 후속 배포 작업의 필수 조건

1. 운영 빌드는 `content/editorial/`을 직접 읽지 않고 `src/data/generated/catalog.json`만 사용한다.
2. 배포 전 `npm run check`를 실행해 기존 정본, 공개 카탈로그, 타입과 프로덕션 빌드를 모두 검사한다.
3. 배포 대상 revision에는 생성 카탈로그와 그 `releaseId`에 해당하는 `content/releases/` 스냅샷이 함께 커밋되어 있어야 한다.
4. 아카이브와 `/events/korea-yonsei-games-2026/`에서 새 공개곡, 수정곡과 공개 해제곡을 스모크 테스트한다.
5. Admin 서버는 현재 내부망 전용 편집 도구로 유지하며 공개 사이트와 같은 외부 접근 범위로 노출하지 않는다.
6. 콘텐츠 공개와 운영 배포는 별도 승인으로 유지한다. 여러 곡을 로컬 공개한 뒤 하나의 운영 릴리스로 묶어 배포할 수 있어야 한다.
7. 운영 배포가 도입되면 Admin에 `로컬 반영`, `운영 배포 대기`, `운영 배포 완료`를 구분해 표시하고 실제 배포 식별자와 콘텐츠 `releaseId`를 함께 기록한다.

현재 저장소에는 배포 대상, 원격 이미지 저장소와 런타임 계약이 확정되어 있지 않다. 후속 배포 작업에서 호스팅 방식과 접근 범위를 먼저 결정하고, 그때 필요한 배포 파일과 승인 절차를 추가한다.
