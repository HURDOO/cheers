# 콘텐츠 수집·편집·배포 운영 규칙

- 상태: 확정
- 확정일: 2026-08-25
- 구현 상태: 반복형 AI 수집·작성 큐, Admin 라벨 관리, 로컬 공개 릴리스와 사이트 데이터 생성 구현
- 적용 범위: 대학·프로야구 응원가 수집, TMI 작성, 영상 선별, 사이트 승인·게시

## 1. 운영 원칙

1. 사용자는 편집자이자 최종 승인자다. 처음부터 모든 문장을 직접 쓸 필요는 없다.
2. AI는 조사, 흥미로운 주제 선정, 공개용 초안 작성, 기존 원고 보강과 자체 검토를 담당한다.
3. TMI는 학술 데이터베이스가 아니라 독자의 흥미를 위한 편집 콘텐츠다.
4. TMI의 출처는 선택 사항이며, 출처가 없다는 이유만으로 작성이나 게시를 막지 않는다.
5. 출처가 있을 때는 별도 주장·증거 데이터로 분해하지 않고 본문 안의 텍스트 주석으로 표시한다.
6. Admin의 편집 데이터가 유일한 작업 정본이다. 사용자가 요청한 AI 작업은 새 편집 revision을 만들 수 있지만 승인이나 공개 상태로 자동 승격하지 않는다.
7. 사용자가 최종 승인한 릴리스 스냅샷만 사이트 공개 데이터로 변환한다.
8. 시스템은 영상·가사의 권리 확인 과정이나 증빙을 관리하지 않는다. 사용자가 추가하고 승인한 콘텐츠는 사용할 수 있는 것으로 신뢰한다.

## 2. 역할 분담

### 사용자

- 대학·구단별 조사 대상과 보류 목록을 제공한다.
- AI가 발견한 추가 응원가를 조사 대상으로 승격하거나 보류·제외한다.
- AI가 작성한 소개, 사용 맥락과 TMI를 읽고 삭제·수정·보완한다.
- 출처를 달지, 어떤 출처를 달지, 상충하는 주장을 어떻게 표현할지 결정한다.
- 사이트에서 보여 줄 대표 영상 하나와 필요한 추가 영상(최대 네 개)의 순서를 직접 선택한다.
- 가사와 영상의 사용 가능 여부를 직접 판단한다.
- 사이트 미리보기를 확인하고 최종 승인한다.

### AI

- 현재 본문을 읽고 지정된 응원가의 흥미로운 이야기와 참고 자료를 탐색한다.
- 조사와 작성을 오가며 기존 본문을 나무위키처럼 편하게 읽히는 공개용 글로 보강한다.
- 조사 중 발견한 누락 응원가를 별도 목록으로 보고한다.
- 사용자가 제공한 링크가 열리는지, 링크 내용이 주석과 명백하게 어긋나지 않는지 확인한다.
- 서로 다른 설이나 구전도 흥미가 있으면 자연스러운 유보 표현과 함께 본문에 포함할 수 있다.
- 작성 도중 맞춤법, 중복, 링크 오류, 구조 누락과 명백한 사실 오류를 자체 검토한다.
- 변경 내용과 불확실한 부분은 공개 본문과 분리된 AI 작업 기록으로 남긴다.

AI는 다음 작업을 하지 않는다.

- 보류곡을 조사 대상으로 자동 승격한다.
- AI가 발견한 곡을 자동으로 본조사한다.
- 대표 영상이나 영상 순서를 정한다.
- 출처가 없다는 이유로 TMI를 거절한다.
- 사용자 대신 최종 승인하거나 게시한다.

### 코드

다음과 같이 결정적으로 검사할 수 있는 작업은 AI가 아니라 코드가 담당한다.

- ID 및 목록 중복
- 필수 UI 필드와 연결 관계
- 영상 순위 중복과 역할 누락
- URL 형식과 YouTube ID
- 작업 revision 충돌
- 릴리스 스냅샷 무결성

## 3. 응원가 목록

목록의 유래와 현재 조사 범위를 분리해 저장한다.

### 발견 주체

- `user`: 사용자가 제공한 곡
- `ai`: AI가 조사 중 추가로 발견한 곡

발견 주체는 곡의 이력이며 나중에 바꾸지 않는다.

### 조사 범위

- `target`: 지금 조사할 곡
- `deferred`: 사용자가 의도적으로 나중으로 미룬 곡
- `discovered_pending`: AI가 발견해 사용자 판단을 기다리는 곡
- `rejected`: 조사하지 않기로 결정한 곡

Admin은 기본적으로 다음 세 목록을 보여 준다.

1. 조사 대상
2. 나중에 조사
3. AI 추가 발견

AI 발견곡을 사용자가 채택하면 조사 범위만 `target`으로 바꾸고 `discoveredBy: ai`는 유지한다. AI는 조사 전에 보류·제외 목록과 별칭을 함께 읽어 이미 보류한 곡을 누락곡으로 반복 보고하지 않는다.

## 4. AI 수집·작성 단위와 결과

기본 작업 단위는 한 곡이다. AI는 현재 공개 본문과 이전 작업 기록을 먼저 읽고, 흥미로운 소재 약 10개를 목표로 조사하면서 글을 직접 보강한다. 10개는 완료 조건이 아니므로 자료가 적으면 억지로 늘리지 않고, 이야기가 풍부하면 더 많이 쓸 수 있다.

수집, 작성과 검토는 서로 분리된 수직 단계가 아니다. AI는 자료를 찾다가 바로 문단을 작성하고, 작성한 문단에서 부족한 부분을 발견하면 다시 조사하며, 제출 전에는 중복과 과도한 단정을 걷어낸다.

공개 본문의 작성 기준은 다음과 같다.

- 가장 의외성이 크거나 재미있는 이야기부터 시작한다.
- 일반적인 사실 목록보다 한 문단에 한 가지 이야기를 담는다.
- 카더라·구전·상충하는 설도 삭제하지 않고 `전해진다`, `라는 이야기가 있다`처럼 자연스럽게 범위를 표시한다.
- 출처는 필요할 때만 `[* ...]` 주석에 넣는다.
- 기존 사용자 문장 중 가치 있는 내용은 보존한다.
- AI식 총평, 반복되는 대표곡 칭찬과 근거 없는 인과관계는 제거한다.

AI는 다음 JSON을 제출한다.

```json
{
  "descriptionText": "기존 글을 반영해 완성한 공개용 전체 본문",
  "researchText": "변경 내용, 불확실한 부분과 추가 발견곡을 적은 검수용 Markdown"
}
```

`descriptionText`는 부분 패치가 아니라 해당 revision의 전체 공개 본문이다. `researchText`는 사용자 검수용 기록이며 공개 사이트에 포함하지 않는다. 출처 없음은 실패 상태가 아니며, AI는 자료를 만들거나 없는 링크를 붙이지 않는다.

## 5. TMI 본문과 주석

소개, 사용하는 상황, 맥락과 TMI는 하나의 자유로운 텍스트 본문으로 작성한다. 내부적으로 Claim, Evidence, 신뢰도 점수나 문장별 검증 상태를 만들지 않는다.

본문은 기본 Markdown과 나무위키식 인라인 주석을 지원한다.

```markdown
이 곡은 처음에는 다른 이름으로 불렸다는 이야기가 있다.[* 원문 출처: https://example.com/source]

자료마다 도입 시점이 다르게 적혀 있다.[* 2011년설: https://example.com/a / 2012년설: https://example.com/b]

현장에서는 보통 경기 막판에 부른다.
```

주석 규칙은 다음과 같다.

- 형식은 `[* 주석 내용]`이다.
- 주석 내용은 일반 텍스트이며 URL을 0개 이상 포함할 수 있다.
- 출처 이름, 판단 근거, 서로 다른 설을 한 주석 안에 자유롭게 적을 수 있다.
- 데스크톱에서는 표식에 마우스를 올리거나 키보드로 초점을 맞추면 내용을 표시한다.
- 모바일에서는 표식을 누르면 내용을 표시한다.
- 주석 안 URL은 사용자가 직접 원문을 열 수 있는 링크로 렌더링한다.
- 주석이 없는 문장도 그대로 게시할 수 있다.

서로 대치되는 주장이 있어도 별도 구조를 강제하지 않는다. AI가 차이를 작업 기록으로 알려 주면 사용자가 다음 중 원하는 방식으로 본문을 쓴다.

- 한 주장을 선택해 서술
- 여러 주장을 주석에 함께 표시
- 본문을 중립적으로 작성
- 출처 없이 작성
- 해당 내용을 제외

AI 검수는 주석이 있을 때 링크와 서술의 명백한 불일치를 알려 주는 보조 작업이다. 검수 결과는 평문과 수정 제안으로 제공하며 출처 유무에 따른 게시 차단 조건을 만들지 않는다.

## 6. Admin 사용자 흐름

### 6.1 대상 관리

Admin은 일반 DB 관리 패널처럼 대학·구단과 응원가를 별도 테이블로 표시한다. 사용자는 대학·구단을 추가·수정·삭제하고, 구단별 응원가를 검색·필터링하며 한 곡씩 추가하거나 목록을 붙여 넣을 수 있다. 응원가 여러 곡을 체크해 AI 수집·작성 요청, 작업 라벨 변경과 조사 범위 변경을 한 번에 실행할 수 있다. 연결된 응원가가 있는 대학·구단은 실수로 삭제되지 않도록 차단하고, 사용자가 이름을 다시 입력해 일괄 삭제를 명시한 경우에만 연결곡과 함께 삭제 기록을 남긴다.

응원가 목록은 조사 대상, 보류와 AI 추가 발견을 필터로 구분하며 제목·별칭 중복 가능성을 알려 준다. 응원가는 다른 대학·구단으로 이동하거나 개별 삭제할 수 있다.

### 6.2 반복형 AI 수집·작성

사용자가 한 곡에서 `AI 수집·작성 요청`을 누르거나 목록에서 여러 곡을 체크해 일괄 요청하면 각 곡의 현재 revision을 기준으로 작업 목록에 올라간다. 이미 대기·진행 중인 곡에는 중복 작업을 만들지 않는다. Naru/Codex는 다음 작업을 받아 현재 본문을 조사·작성·자체 검토한 뒤 보강된 전체 본문을 제출한다. 완료된 곡에는 `수집 완료` 작업 라벨이 붙는다.

사용자는 결과를 검수해 직접 수정하거나 필요 없는 문단을 지운다. 더 보완해야 하면 같은 곡을 다시 작업 목록에 올리고, 충분하면 `승인` 라벨을 선택한다. 반복 횟수와 순서는 고정하지 않는다.

### 6.3 작업 라벨과 필터

작업 라벨은 강제 전이 규칙이 없는 사용자 관리용 태그다. 곡 목록과 편집 화면의 드롭다운에서 언제든 바꿀 수 있다. 목록에서는 대학·구단, 조사 범위, 작업 라벨과 최신 AI 작업 상태로 필터링한다.

AI 작업 상태는 라벨과 분리한다. `대기 중`, `진행 중`, `최근 완료`, `무효화됨`, `작업 없음`으로 표시한다. 사용자가 작업 요청 뒤 본문을 수정해 revision이 달라지면 해당 작업은 무효화되고 최신 revision으로 다시 요청할 수 있다.

### 6.4 고연전 작업 우선순위

Admin의 `작업 순서` 화면은 `src/events/korea-yonsei-games-2026/eventCuration.json`을 이벤트 큐의 단일 기준으로 읽는다. 행사 중요도는 다음 순서로 고정하고, 같은 등급 안에서는 공개 직전의 작업을 먼저 보여 준다.

1. `P0` 필수 암기
2. `P1` 라이벌전
3. `P2` 추억곡
4. `P3` 원곡 계보
5. `P4` 야구장 연결
6. `P5` 양교 추가곡

각 행은 ChatGPT가 맡을 조사·편집·QA와 사용자가 맡을 영상·가사·상징문구 확인 및 공개를 분리해 표시한다. `ChatGPT 요청 복사`는 해당 곡 ID, 현재 상태, 빈 항목과 역할 경계를 포함한 한 곡 단위 요청문을 만든다. ChatGPT는 `review_ready`까지만 이동할 수 있으며 공개·재공개는 사용자가 직접 실행한다.

이벤트 큐에 있지만 Admin에 없는 곡과 원곡 정본·관계 누락도 작업 목록에 표시한다. 누락곡의 `빈 레코드 추가`는 ID, 제목과 소속만 미리 채우며 조사 결과를 자동 승인하지 않는다. 우선순위는 작업 계획일 뿐 게시 차단 규칙이 아니며 사용자는 필터와 일반 응원가 화면을 통해 어떤 곡이든 먼저 작업할 수 있다.

### 6.5 영상 선별

사용자가 YouTube에서 찾은 URL을 추가하면 Admin은 영상 제목, 채널, 썸네일을 불러온다. 대표 영상 하나를 기본으로 하고 추가 영상은 필요할 때 최대 네 개까지 등록한다. 메타데이터 조회는 영상 내용이나 재생 가능 여부의 검수를 대신하지 않으며 사용자가 재생해서 확인한다. 조회 실패 시에도 직접 입력하고 저장할 수 있다.

1. 대표 영상: 떼창과 분위기가 잘 드러나는 사용자가 선택한 영상
2. 추가 영상: 공식·가사 영상, 다른 분위기나 시기의 현장 영상 등 최대 네 개

기존에 저장한 영상과 순서는 유지한다. 설명·가사·영상은 편집 탭으로 오가고, 기본 정보·관계·AI 작업 기록·공개 관리는 `기본·관리` 탭에서 확인한다. 저장 후 현재 곡을 계속 편집하거나 현재 필터의 다음 곡으로 이동할 수 있다. 미저장 입력은 브라우저에 임시 보관하며, 다른 revision에서 작성한 임시본은 최신 저장본에 자동 적용하지 않는다.

AI는 사용자가 고른 URL의 형식과 상태를 확인할 수 있지만 검색 결과에서 영상을 대신 고르거나 순위를 바꾸지 않는다.

### 6.6 AI 자체 검토와 사용자 검수

AI는 조사·작성 작업 안에서 맞춤법, 읽기 어려운 문장, 내용 중복, 깨진 링크와 크게 충돌할 표현을 자체 검토한다. 사용자는 완성된 본문을 기준으로 문단을 삭제·수정하고 필요하면 같은 작업을 다시 요청한다.

### 6.7 미리보기와 최종 승인

Admin에서 실제 공개 화면과 같은 미리보기를 확인한다. 사용자가 `공개`를 선택하거나 `사이트에 공개`를 실행하면 현재 revision으로 불변 릴리스 스냅샷을 만들고, 이 스냅샷에서 로컬 사이트용 데이터를 생성한다. 승인된 내용을 수정해도 기존 공개본은 유지되며 `재공개 필요`로 표시한다. 사용자가 재공개해야 새 revision이 다음 릴리스에 들어간다. 로컬 공개는 운영 서버 배포를 실행하지 않는다.

## 7. Admin과 Naru/Codex 연결

1차 구현에서는 Naru를 수정하지 않는다. `cheers` 프로젝트에 작업 큐와 프로젝트 전용 CLI를 두고, Naru의 Codex가 같은 프로젝트에서 작업을 가져가도록 한다.

```text
Admin에서 작업 생성
  → 로컬 작업 큐에 job과 inputRevision 저장
  → Naru/Codex가 프로젝트 CLI로 다음 job 수령
  → AI가 현재 글을 읽고 수집·작성·검토를 반복
  → 보강한 전체 공개 본문과 검수용 작업 기록 제출
  → 스키마와 revision 검사
  → 수집 완료 라벨에서 사용자 검수
  → 필요하면 다시 큐에 등록, 충분하면 승인
  → 릴리스 스냅샷과 사이트 데이터 생성
```

예상 CLI 표면은 다음과 같다.

```bash
pnpm content:next
pnpm content:work <job-id>
pnpm content:submit <job-id>
```

Naru에서는 사용자가 “다음 응원가 작업 진행해줘”라고 요청하면 프로젝트 지침이 다음 작업을 찾도록 한다. 작업 규칙은 Codex 대화 기억에 의존하지 않고 job의 운영 규칙 버전과 프로젝트 문서에서 읽는다.

AI 작업 중 원고가 수정되어 revision이 달라지면 결과를 자동 반영하지 않는다. 결과는 오래된 입력을 기준으로 한 제안으로 보존하고 Admin에서 사용자에게 알려 준다.

Admin과 Codex는 JSON 파일을 각자 임의 수정하지 않고 같은 도메인 라이브러리와 CLI를 통해 읽고 쓴다. 작업 대기열, 잠금과 실행 상태는 Git에 넣지 않는 로컬 저장소에 두고, 사용자가 받아들인 편집 데이터와 릴리스 스냅샷만 버전 관리한다.

Admin에서 Codex를 직접 시작하고 진행 이벤트와 승인 요청까지 표시할 필요가 생기면 Naru의 일반 목적 Agent Job 기능을 별도 2단계로 설계한다. 1차 구현에서는 PTY에 키 입력을 주입하거나 Naru 내부 DB를 직접 수정하지 않는다.

## 8. 편집 데이터 구조

TMI를 위해 별도의 Source, Claim, Evidence 테이블을 만들지 않는다. UI 동작과 관계에 필요한 값만 구조화하고 서술과 주석은 텍스트로 둔다.

```text
content/
  editorial/
    organizations/
    songs/
      <song-id>/
        song.json       # 곡 정보, 본문, 영상 선택, 작업 라벨
        research.md     # 최근 AI 작업 내역과 검수 메모
  releases/
    <release-id>.json   # 최종 승인된 불변 스냅샷

src/data/generated/     # 사이트가 읽는 생성 데이터
.local/                 # 작업 큐·잠금·실행 상태, Git 제외
```

편집 곡의 핵심 개념은 다음과 같다.

```json
{
  "id": "song-id",
  "organizationId": "organization-id",
  "discoveredBy": "user",
  "scopeStatus": "target",
  "workflowStage": "editing",
  "title": "응원가 제목",
  "aliases": [],
  "descriptionText": "소개와 TMI.[* 원문 출처: https://example.com]",
  "lyrics": {
    "lines": [],
    "collapsedPreviewLineCount": 2
  },
  "quickFacts": [],
  "videos": [],
  "relationships": [],
  "revision": 1
}
```

정확한 필드명은 구현 전 스키마 설계에서 확정하되 다음 경계는 유지한다.

- 서술과 출처 주석은 `descriptionText` 안의 텍스트다.
- 영상 순위, 가사 줄, 간단 정보와 원곡 계보는 UI가 사용하므로 구조화한다.
- AI 작업 기록과 공개 본문은 분리하지만 AI는 사용자 요청이 있을 때 공개 본문의 새 편집 revision을 작성할 수 있다.
- 공개 데이터에는 작업 큐, AI 실행 기록과 내부 메모를 포함하지 않는다.

## 9. 공개 상세 화면

1. 헤더: 곡 제목과 대학·구단 표시를 현재와 같이 유지한다.
2. 영상: 사용자 선택 순서대로 다섯 개를 표시한다.
3. 가사: 처음 두 줄을 먼저 보여 주고 전체는 펼치기·접기로 표시한다.
4. 간단 정보: 순서 있는 세 항목을 표시한다. 첫 항목은 사용 시작 시점으로 고정하고 나머지 두 항목은 추후 확정한다.
5. 설명: 소개, 사용 상황, 맥락과 TMI를 하나의 본문으로 표시하고 `[* ...]` 주석을 상호작용 가능한 표식으로 렌더링한다.
6. 원곡 계보·같은 원곡 응원가: 현재 기능을 유지한다.

시스템은 영상·가사의 허락 상태, 허용 플랫폼, 증빙, 만료일 같은 권리 확인 필드를 저장하지 않는다. 사용자가 선택하고 최종 승인한 영상과 가사는 사용할 수 있는 것으로 간주한다. 영상이나 쇼츠에 실제로 노출할 출처·크레딧 문구가 필요하면 권리 증빙이 아니라 공개 콘텐츠의 일부인 일반 텍스트로만 저장한다.

## 10. 콘텐츠 작업 라벨

보류 여부와 작업 라벨은 별개다. 라벨은 순서가 있는 워크플로가 아니라 사용자가 자유롭게 바꾸는 분류값이다.

- `listed`: 시작 전
- `needs_work`: 보완 필요
- `researching`: AI 조사 중이라는 기존 호환 라벨
- `research_ready`: 수집 완료
- `editing`: 편집 중
- `review_ready`: 검수 대기
- `approved`: 승인
- `published`: 공개

어떤 라벨에서도 AI 작업을 다시 요청할 수 있다. AI 제출은 `research_ready`까지만 자동 지정하며 `approved`와 `published`는 사용자가 직접 선택한다. `published` 선택은 단순 라벨 변경이 아니라 로컬 사이트 공개 동작을 함께 실행한다. 공개한 뒤 본문을 저장했다고 기존 공개본을 자동 교체하지 않으며, 공개 상태와 편집 revision의 내용 해시 차이로 `재공개 필요`를 판단한다.

공개 상태는 작업 라벨과 별도로 `미공개`, `사이트 반영됨`, `재공개 필요`로 표시한다. 공개를 내리면 새 릴리스에서 해당 곡을 제외하고 작업 라벨은 `승인`으로 돌아간다. 과거 릴리스 파일은 삭제하지 않는다.

## 11. 기존 데이터 처리

- 현재 사용자가 검수한 23곡은 기존 공개 스냅샷으로 유지한다.
- 새 편집 체계로 옮길 때 제목, 소속, 원곡 계보와 사용자가 승인한 정보만 초기값으로 사용한다.
- 과거 대량 AI 조사 결과와 AI가 작성한 설명은 새 편집 정본으로 자동 이관하지 않는다.
- 새 스키마가 구현되기 전까지 현행 `schemaVersion: 1` 데이터와 검증 규칙은 그대로 동작한다.

## 12. 확정한 제외 사항

이번 운영 체계에서는 다음 기능을 만들지 않는다.

- 문장별 Claim·Evidence 그래프
- 출처 신뢰도 점수
- 출처 개수에 따른 게시 차단
- 무출처 TMI 경고를 해소해야만 승인되는 절차
- 영상·가사의 권리 상태, 허용 범위와 증빙을 기록하는 필드
- AI 자동 영상 선별·자동 승인
- 기존 대량 AI 조사 데이터의 자동 복원
