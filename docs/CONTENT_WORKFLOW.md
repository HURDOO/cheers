# 콘텐츠 수집·편집·배포 운영 규칙

- 상태: 확정
- 확정일: 2026-08-25
- 구현 상태: 구현 전
- 적용 범위: 대학·프로야구 응원가 수집, TMI 작성, 영상 선별, 사이트 승인·게시

## 1. 운영 원칙

1. 사용자가 편집자이자 최종 작성자다.
2. AI는 조사, 빠진 응원가 발견, 링크 확인, 가벼운 원고 검수와 데이터 가공을 담당한다.
3. TMI는 학술 데이터베이스가 아니라 독자의 흥미를 위한 편집 콘텐츠다.
4. TMI의 출처는 선택 사항이며, 출처가 없다는 이유만으로 작성이나 게시를 막지 않는다.
5. 출처가 있을 때는 별도 주장·증거 데이터로 분해하지 않고 본문 안의 텍스트 주석으로 표시한다.
6. Admin의 편집 데이터가 유일한 작업 정본이다. AI 결과는 제안이며 자동으로 정본을 덮어쓰지 않는다.
7. 사용자가 최종 승인한 릴리스 스냅샷만 사이트 공개 데이터로 변환한다.
8. 시스템은 영상·가사의 권리 확인 과정이나 증빙을 관리하지 않는다. 사용자가 추가하고 승인한 콘텐츠는 사용할 수 있는 것으로 신뢰한다.

## 2. 역할 분담

### 사용자

- 대학·구단별 조사 대상과 보류 목록을 제공한다.
- AI가 발견한 추가 응원가를 조사 대상으로 승격하거나 보류·제외한다.
- AI 조사 자료를 참고해 소개, 사용 맥락과 TMI를 직접 작성한다.
- 출처를 달지, 어떤 출처를 달지, 상충하는 주장을 어떻게 표현할지 결정한다.
- 사이트에서 보여 줄 영상 다섯 개와 순서를 직접 선택한다.
- 가사와 영상의 사용 가능 여부를 직접 판단한다.
- 사이트 미리보기를 확인하고 최종 승인한다.

### AI

- 지정된 응원가의 흥미로운 이야기와 참고 자료를 탐색한다.
- 조사 중 발견한 누락 응원가를 별도 목록으로 보고한다.
- 사용자가 제공한 링크가 열리는지, 링크 내용이 주석과 명백하게 어긋나지 않는지 확인한다.
- 서로 다른 설이 있거나 확신하기 어려운 내용은 평문으로 함께 보고한다.
- 맞춤법, 중복, 링크 오류, 구조 누락과 명백한 사실 오류 후보를 알려 준다.
- 사용자 원고를 운영 스키마에 맞는 배포 후보로 가공한다.

AI는 다음 작업을 하지 않는다.

- 최종 TMI 문체를 대신 결정하거나 사용자 승인 없이 다시 쓴다.
- 보류곡을 조사 대상으로 자동 승격한다.
- AI가 발견한 곡을 자동으로 본조사한다.
- 대표 영상이나 영상 순서를 정한다.
- 출처가 없다는 이유로 TMI를 거절한다.
- 사용자 대신 최종 승인하거나 게시한다.

### 코드

다음과 같이 결정적으로 검사할 수 있는 작업은 AI가 아니라 코드가 담당한다.

- ID 및 목록 중복
- 필수 UI 필드와 연결 관계
- 영상 순위 중복과 역할 누락
- URL 형식과 YouTube ID
- 작업 revision 충돌
- 릴리스 스냅샷 무결성

## 3. 응원가 목록

목록의 유래와 현재 조사 범위를 분리해 저장한다.

### 발견 주체

- `user`: 사용자가 제공한 곡
- `ai`: AI가 조사 중 추가로 발견한 곡

발견 주체는 곡의 이력이며 나중에 바꾸지 않는다.

### 조사 범위

- `target`: 지금 조사할 곡
- `deferred`: 사용자가 의도적으로 나중으로 미룬 곡
- `discovered_pending`: AI가 발견해 사용자 판단을 기다리는 곡
- `rejected`: 조사하지 않기로 결정한 곡

Admin은 기본적으로 다음 세 목록을 보여 준다.

1. 조사 대상
2. 나중에 조사
3. AI 추가 발견

AI 발견곡을 사용자가 채택하면 조사 범위만 `target`으로 바꾸고 `discoveredBy: ai`는 유지한다. AI는 조사 전에 보류·제외 목록과 별칭을 함께 읽어 이미 보류한 곡을 누락곡으로 반복 보고하지 않는다.

## 4. AI 조사 단위와 결과

초기 기본값은 한 작업당 3곡이다. 결과 품질과 사용자 검토 속도가 안정되면 5곡까지 늘린다.

곡당 기본 조사 목표는 다음과 같다.

- 관련 페이지·영상 약 4~6개 탐색
- 흥미로운 TMI 후보 2~4개 제안
- 새로 발견한 응원가는 별도 보고

이 숫자는 조사 노력의 가이드일 뿐 완료 조건이 아니다. 자료가 적으면 더 적게 제출하고, 출처 없이 전해지는 흥미로운 이야기도 후보로 제출할 수 있다. 반대로 대표곡이나 논쟁적인 곡은 사용자가 심층 조사를 지정해 범위를 늘릴 수 있다.

AI 조사 결과는 완성된 소개문이 아니라 읽기 쉬운 텍스트 메모로 제출한다.

```markdown
## TMI 후보

- 이 곡은 처음에는 현재와 다른 제목으로 불렸다는 이야기가 있다.
  - 참고: https://example.com/source
  - 다른 자료에서는 현재 제목이 처음부터 쓰였다고 설명한다: https://example.com/other

- 경기 막판보다 행사 엔딩에서 더 자주 쓰인다는 이야기가 있다.
  - 별도 출처 없음

## 추가 발견곡

- 응원가 이름 — 발견 경로 또는 참고 URL
```

출처 없음은 실패 상태가 아니다. AI는 자료를 찾지 못했다면 그 사실만 적고 내용을 지우거나 만들어 낸 출처를 붙이지 않는다.

## 5. TMI 본문과 주석

소개, 사용하는 상황, 맥락과 TMI는 하나의 자유로운 텍스트 본문으로 작성한다. 내부적으로 Claim, Evidence, 신뢰도 점수나 문장별 검증 상태를 만들지 않는다.

본문은 기본 Markdown과 나무위키식 인라인 주석을 지원한다.

```markdown
이 곡은 처음에는 다른 이름으로 불렸다는 이야기가 있다.[* 원문 출처: https://example.com/source]

자료마다 도입 시점이 다르게 적혀 있다.[* 2011년설: https://example.com/a / 2012년설: https://example.com/b]

현장에서는 보통 경기 막판에 부른다.
```

주석 규칙은 다음과 같다.

- 형식은 `[* 주석 내용]`이다.
- 주석 내용은 일반 텍스트이며 URL을 0개 이상 포함할 수 있다.
- 출처 이름, 판단 근거, 서로 다른 설을 한 주석 안에 자유롭게 적을 수 있다.
- 데스크톱에서는 표식에 마우스를 올리거나 키보드로 초점을 맞추면 내용을 표시한다.
- 모바일에서는 표식을 누르면 내용을 표시한다.
- 주석 안 URL은 사용자가 직접 원문을 열 수 있는 링크로 렌더링한다.
- 주석이 없는 문장도 그대로 게시할 수 있다.

서로 대치되는 주장이 있어도 별도 구조를 강제하지 않는다. AI가 차이를 조사 메모로 알려 주면 사용자가 다음 중 원하는 방식으로 본문을 쓴다.

- 한 주장을 선택해 서술
- 여러 주장을 주석에 함께 표시
- 본문을 중립적으로 작성
- 출처 없이 작성
- 해당 내용을 제외

AI 검수는 주석이 있을 때 링크와 서술의 명백한 불일치를 알려 주는 보조 작업이다. 검수 결과는 평문과 수정 제안으로 제공하며 출처 유무에 따른 게시 차단 조건을 만들지 않는다.

## 6. Admin 사용자 흐름

### 6.1 대상 관리

Admin은 일반 DB 관리 패널처럼 대학·구단과 응원가를 별도 테이블로 표시한다. 사용자는 대학·구단을 추가·수정·삭제하고, 구단별 응원가를 검색·필터링하며 한 곡씩 추가하거나 목록을 붙여 넣을 수 있다. 연결된 응원가가 있는 대학·구단은 실수로 삭제되지 않도록 차단하고, 사용자가 이름을 다시 입력해 일괄 삭제를 명시한 경우에만 연결곡과 함께 삭제 기록을 남긴다.

응원가 목록은 조사 대상, 보류와 AI 추가 발견을 필터로 구분하며 제목·별칭 중복 가능성을 알려 준다. 응원가는 다른 대학·구단으로 이동하거나 개별 삭제할 수 있다.

### 6.2 조사 요청

사용자가 곡을 선택해 조사 작업을 만든다. 작업에는 대상 곡, 입력 revision, 운영 규칙 버전과 요청 시각을 기록한다.

### 6.3 조사 자료 확인

AI가 제출한 TMI 후보, 참고 URL, 상충하는 설명과 추가 발견곡을 텍스트로 보여 준다. 사용자는 이를 참고만 하거나 원고에 복사해 사용할 수 있다.

### 6.4 원고 작성

사용자는 소개, 사용 맥락과 TMI를 하나의 본문 편집기에서 직접 작성한다. 편집기는 `[* ...]` 주석을 미리보기로 렌더링한다.

### 6.5 영상 선별

사용자가 YouTube에서 찾은 URL을 추가하면 Admin은 영상 제목, 채널, 썸네일, 재생 가능 여부 같은 메타데이터를 확인한다. 사용자가 직접 다섯 슬롯을 채우고 순서를 정한다.

1. 공식 또는 가사 영상
2. 대표 현장 직캠
3. 추가 영상
4. 추가 영상
5. 추가 영상

AI는 사용자가 고른 URL의 형식과 상태를 확인할 수 있지만 검색 결과에서 영상을 대신 고르거나 순위를 바꾸지 않는다.

### 6.6 가벼운 AI 검수

AI는 다음 사항을 제안 형태로 보고한다.

- 맞춤법과 읽기 어려운 문장
- 내용 중복
- 깨진 링크 또는 주석과 명백히 관계없는 링크
- 조사 자료와 크게 충돌할 가능성이 있는 표현
- 사이트 필수 데이터 누락

사용자 본문을 자동으로 덮어쓰지 않으며 모든 수정안은 사용자가 수락하거나 거절한다.

### 6.7 미리보기와 최종 승인

Admin에서 실제 공개 화면과 같은 미리보기를 확인한다. 사용자의 최종 승인으로 불변 릴리스 스냅샷을 만들고, 이 스냅샷에서 사이트용 데이터를 생성한다. 승인된 내용을 수정하려면 새 편집 revision과 새 승인을 만든다.

## 7. Admin과 Naru/Codex 연결

1차 구현에서는 Naru를 수정하지 않는다. `cheers` 프로젝트에 작업 큐와 프로젝트 전용 CLI를 두고, Naru의 Codex가 같은 프로젝트에서 작업을 가져가도록 한다.

```text
Admin에서 작업 생성
  → 로컬 작업 큐에 job과 inputRevision 저장
  → Naru/Codex가 프로젝트 CLI로 다음 job 수령
  → AI가 텍스트 조사 메모 또는 검수 제안 제출
  → 스키마와 revision 검사
  → Admin에서 결과 확인
  → 사용자 반영·최종 승인
  → 릴리스 스냅샷과 사이트 데이터 생성
```

예상 CLI 표면은 다음과 같다.

```bash
pnpm content:next
pnpm content:work <job-id>
pnpm content:submit <job-id>
```

Naru에서는 사용자가 “다음 응원가 조사 작업 진행해줘”라고 요청하면 프로젝트 지침이 다음 작업을 찾도록 한다. 작업 규칙은 Codex 대화 기억에 의존하지 않고 job의 운영 규칙 버전과 프로젝트 문서에서 읽는다.

AI 작업 중 원고가 수정되어 revision이 달라지면 결과를 자동 반영하지 않는다. 결과는 오래된 입력을 기준으로 한 제안으로 보존하고 Admin에서 사용자에게 알려 준다.

Admin과 Codex는 JSON 파일을 각자 임의 수정하지 않고 같은 도메인 라이브러리와 CLI를 통해 읽고 쓴다. 작업 대기열, 잠금과 실행 상태는 Git에 넣지 않는 로컬 저장소에 두고, 사용자가 받아들인 편집 데이터와 릴리스 스냅샷만 버전 관리한다.

Admin에서 Codex를 직접 시작하고 진행 이벤트와 승인 요청까지 표시할 필요가 생기면 Naru의 일반 목적 Agent Job 기능을 별도 2단계로 설계한다. 1차 구현에서는 PTY에 키 입력을 주입하거나 Naru 내부 DB를 직접 수정하지 않는다.

## 8. 편집 데이터 구조

TMI를 위해 별도의 Source, Claim, Evidence 테이블을 만들지 않는다. UI 동작과 관계에 필요한 값만 구조화하고 서술과 주석은 텍스트로 둔다.

```text
content/
  editorial/
    organizations/
    songs/
      <song-id>/
        song.json       # 곡 정보, 본문, 영상 선택, 진행 상태
        research.md     # 사용자가 참고할 AI 조사 메모
  releases/
    <release-id>.json   # 최종 승인된 불변 스냅샷

src/data/generated/     # 사이트가 읽는 생성 데이터
.local/                 # 작업 큐·잠금·실행 상태, Git 제외
```

편집 곡의 핵심 개념은 다음과 같다.

```json
{
  "id": "song-id",
  "organizationId": "organization-id",
  "discoveredBy": "user",
  "scopeStatus": "target",
  "workflowStage": "editing",
  "title": "응원가 제목",
  "aliases": [],
  "descriptionText": "소개와 TMI.[* 원문 출처: https://example.com]",
  "lyrics": {
    "lines": [],
    "collapsedPreviewLineCount": 2
  },
  "quickFacts": [],
  "videos": [],
  "relationships": [],
  "revision": 1
}
```

정확한 필드명은 구현 전 스키마 설계에서 확정하되 다음 경계는 유지한다.

- 서술과 출처 주석은 `descriptionText` 안의 텍스트다.
- 영상 순위, 가사 줄, 간단 정보와 원곡 계보는 UI가 사용하므로 구조화한다.
- AI 조사 원문과 공개 본문은 분리한다.
- 공개 데이터에는 작업 큐, AI 실행 기록과 내부 메모를 포함하지 않는다.

## 9. 공개 상세 화면

1. 헤더: 곡 제목과 대학·구단 표시를 현재와 같이 유지한다.
2. 영상: 사용자 선택 순서대로 다섯 개를 표시한다.
3. 가사: 처음 두 줄을 먼저 보여 주고 전체는 펼치기·접기로 표시한다.
4. 간단 정보: 순서 있는 세 항목을 표시한다. 첫 항목은 사용 시작 시점으로 고정하고 나머지 두 항목은 추후 확정한다.
5. 설명: 소개, 사용 상황, 맥락과 TMI를 하나의 본문으로 표시하고 `[* ...]` 주석을 상호작용 가능한 표식으로 렌더링한다.
6. 원곡 계보·같은 원곡 응원가: 현재 기능을 유지한다.

시스템은 영상·가사의 허락 상태, 허용 플랫폼, 증빙, 만료일 같은 권리 확인 필드를 저장하지 않는다. 사용자가 선택하고 최종 승인한 영상과 가사는 사용할 수 있는 것으로 간주한다. 영상이나 쇼츠에 실제로 노출할 출처·크레딧 문구가 필요하면 권리 증빙이 아니라 공개 콘텐츠의 일부인 일반 텍스트로만 저장한다.

## 10. 콘텐츠 진행 상태

보류 여부와 편집 진행 상태는 별개다. 편집 진행 상태는 다음 흐름을 기본으로 한다.

```text
listed
  → researching
  → research_ready
  → editing
  → review_ready
  → approved
  → published
```

검수 후 수정이 필요하면 `editing`으로 돌아간다. 게시된 곡을 수정할 때도 기존 릴리스를 덮어쓰지 않고 새 revision에서 같은 흐름을 반복한다.

## 11. 기존 데이터 처리

- 현재 사용자가 검수한 23곡은 기존 공개 스냅샷으로 유지한다.
- 새 편집 체계로 옮길 때 제목, 소속, 원곡 계보와 사용자가 승인한 정보만 초기값으로 사용한다.
- 과거 대량 AI 조사 결과와 AI가 작성한 설명은 새 편집 정본으로 자동 이관하지 않는다.
- 새 스키마가 구현되기 전까지 현행 `schemaVersion: 1` 데이터와 검증 규칙은 그대로 동작한다.

## 12. 확정한 제외 사항

이번 운영 체계에서는 다음 기능을 만들지 않는다.

- 문장별 Claim·Evidence 그래프
- 출처 신뢰도 점수
- 출처 개수에 따른 게시 차단
- 무출처 TMI 경고를 해소해야만 승인되는 절차
- 영상·가사의 권리 상태, 허용 범위와 증빙을 기록하는 필드
- AI 자동 원고 작성·자동 영상 선별·자동 승인
- 기존 대량 AI 조사 데이터의 자동 복원
